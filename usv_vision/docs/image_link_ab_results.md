# 图像链路改造：全量对比记录（2026-11-07）

测试平台：NVIDIA Jetson AGX Orin 32GB（L4T R36.4.7 / JetPack 6.2.1 / CUDA 12.6 / TensorRT 10.3.0）
软件栈：torch 2.11.0（jetson CUDA 版）+ torchvision 0.26.0 + ultralytics 8.4.147 + numpy 1.26.4
相机：三路 GMSL（front=/dev/video0, right=/dev/video1, left=/dev/video2），1920×1536 @ 30fps
模型：yolo11n（COCO 预训练，仅用于验证链路性能，不含 boat 类）
功耗模式：MAXN；满载时 GPU 930MHz（该板上限 931MHz）、CPU 2188MHz（上限 2189MHz）

> 口径说明：所有 CPU 百分比均为**单核基准**（100% = 占满 1 个物理核）；换算整机占用需除以 8。

---

## 一、改造前后是什么

| | 改造前（旧形态） | 改造后（按需分发） |
|---|---|---|
| 采集发布 | 只发 `image_raw`（全分辨率 8.8MB） | 同时发 `image_raw`（全分辨率）+ `image_algo`（640×640，1.2MB） |
| 识别输入 | 订阅 `image_raw`，自己做 letterbox/resize | 订阅 `image_algo`（1.2MB） |
| 推流输入 | 订阅 `image_raw` | 不变 |
| 每帧每相机 DDS 写出量 | 8.8MB × 2 个读者 = **17.6MB** | 8.8MB（推流）+ 1.2MB（识别）= **10.0MB** |
| QoS | 发布 reliable/depth10，订阅 best_effort | 发布 reliable/depth2，订阅 best_effort/depth1 |
| 无订阅者时 | 照常发布 | **不 resize、不发布**（零开销） |

- `image_raw` 带宽实测 **264.58 MB/s**（8.8MB × 30）

## 五、做过的其他优化尝试与结论

| 尝试 | 结果 | 结论 |
|---|---|---|
| `cv::setNumThreads(1)`（限制 OpenCV 线程） | 单路：无订阅 24~26%→**17.0%**，有订阅 64%→**50.3%** | ✅ 已采用（多线程 resize 的 CPU 时间≈墙钟×线程数） |
| `camera_info_algo` 改 1Hz 重发 | 变化在噪声内 | 保留（无副作用，语义更合理） |
| `trtexec --builderOptimizationLevel` 0 vs 3 | 总 GPU 时间 3.012s vs 3.004s | ❌ 无收益，不折腾 |
| `--memPoolSize` 显式指定 | **导致 engine 构建失败**（报 insufficient workspace） | ❌ 不要加；用 `--fp16 --builderOptimizationLevel=0` 即可 |
| 开启蒙板（`enable_mask: true`） | 识别 CPU 39.6%→**55.2%**，`detections` 26.1→**22.0Hz**，`infer` +10ms | ⚠️ 默认关闭；确需开启建议每 N 帧更新 mask 或下沉到 C++ |
| 发布端 reliable + 订阅端 best_effort | 冻结可靠读者（rosbag SIGSTOP）出帧率仍 29Hz | ✅ 反压安全，方案成立 |

## 六、结论

1. **帧率没有提升**，因为三路时 **GPU 已跑在上限频率（930MHz）且占用 83%**，瓶颈是 GPU 算力，不是 CPU 搬运。
2. **省下来的是资源**：CPU −6%、内存 −4%、DDS 带宽 −43%、识别端每帧搬运 −86%。
3. **视觉在三路全开时是整机最大消耗者**：CPU 51%、GPU 75%、内存 +3.6GB；留给其它模块约 3.7 核 / 19GB / 25% GPU。
4. 因此**第 4 路相机加不进来**（GPU 只剩 25% 余量）。
5. 早期"吞吐 +44%"的结论作废——那是启动预热期的假数据，实测复测后两者持平。

## 八、测量方法与可信度说明

- **出帧率**：用 `ros2 topic hz` 订阅轻量的 `frame_timing_json`（一帧一条），不用 `image_raw`（8.8MB 的 Python 订阅会跟不上，会把 30Hz 误报成 16Hz）。
- **进程 CPU**：读 `/proc/<pid>/stat` 的 utime+stime 增量 ÷ CLK_TCK ÷ 时间窗（10~12s），不用 `ps` 瞬时值（噪声极大）。
- **GPU / 频率 / 功耗 / 温度**：`tegrastats` 与 `/sys/class/devfreq/17000000.gpu/cur_freq`。
- **对照控制**：同一份代码用 `use_algo_image` 开关切换数据路径，保证除被测量外其余条件一致；测量前清理残留进程与 GUI 负载。
- **已知噪声**：启动后 20s 内 engine 预热，必须跳过；三路顺次启动时各路 GPU 时钟爬升不同。
