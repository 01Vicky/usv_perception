# 视觉链路性能优化报告

**日期**：2026-11-07　**平台**：米文主机 NVIDIA Jetson AGX Orin 32GB（JetPack 6.2 / TensorRT 10.3）
**范围**：`usv_vision_gmsl_cpp`、`usv_vision` 两个视觉包（三路 GMSL 相机，1920×1536@30fps）

---

## 一、结论（先看这一页）

1. **主要收益来自"把视频编码从 Python 进程搬进 C++ 采集进程"。**
   三路相机全开（采集 + 推理 + 推流）时，**视觉 CPU 从 3.69 核降到 2.90 核（−21%）**，
   **整机 CPU 从 51.8% 降到 41.8%（−10 个百分点）**，**内存减少 0.6GB**。
2. **图像质量与实时性没有牺牲**：三路均保持 1920×1536@30fps，画质对比 PSNR **43.8dB**（>40dB 即肉眼难辨）。
3. **通信开销大幅下降**：每帧每相机的 DDS 写出量从 **17.6MB 降到 1.2MB（−93%）**，
   三路总带宽从约 **1.58GB/s 降到 0.11GB/s**。
4. **该结论是在锁定频率（GPU 931MHz / CPU 2189MHz）、30s 预热、3×20s 取中位数下测得的**，
   可复现，不是估算。
5. 另有 5 项常见优化手段经实测**无效**（见第五节），已排除，避免后续重复投入。

## 二、改造前后的数据流架构

### 2.1 改造前

```
 相机(1920×1536 BGRA)
   │
   ▼
 C++ 采集节点 ──image_raw 8.8MB──▶ DDS ──▶ Python 识别节点（自己做 resize 到 640）
   │                        └──────▶ DDS ──▶ Python 推流节点（bytes 拷贝 → videoconvert → nvvidconv → H.264 → RTSP）
   │
   └─ 每帧每相机 DDS 写出 8.8MB × 2 个读者 = 17.6MB
```

**问题**：同一帧被写了两遍（识别、推流各一份 8.8MB），推流还要在 Python 里再做一次软件转色。

### 2.2 改造后

```
 相机(1920×1536 BGRA)
   │
   ▼
 C++ 采集节点 ──┬── image_raw 8.8MB ──▶ DDS（保留给其它需要全分辨率的消费者）
                │
                ├── image_algo 1.2MB ──▶ DDS ──▶ Python 识别节点（直接用 640 小图，不再缩放）
                │
                └── 内置推流线程（同进程）──▶ BGRx → nvvidconv → 硬件 H.264 → RTSP
                                                （不经 DDS、不进 Python、无软件转色）

 每帧每相机 DDS 写出 = 1.2MB（仅识别）；推流零 DDS
```

**关键变化**：

| 变化 | 说明 |
|---|---|
| 按需分发 | 采集端一次成帧，同时产出全分辨率图与 640 算法图，识别只取小图 |
| 编码内移 | H.264 编码在采集进程内的独立线程完成，绕过 DDS 与 Python 解释器 |
| 格式对位 | 直接用 BGRx 送 `nvvidconv`（硬件），彻底去掉软件 `videoconvert` |
| 实时性保障 | 推流线程队列满即丢旧帧，采集线程**从不等待编码**；断线 3 秒自动重建 |

## 三、通信资源开销对比

| 指标 | 改造前 | 改造后 | 变化 |
|---|---|---|---|
| 每帧每相机 DDS 写出 | **17.6 MB**（8.8×2 读者） | **1.2 MB** | **−93%** |
| 三路每帧 DDS 总量 | 52.8 MB | 3.6 MB | −93% |
| **三路 DDS 带宽** | **≈1.58 GB/s** | **≈0.11 GB/s** | **−93%** |
| 识别端每帧搬运 | 8.8 MB + 自身 resize 2.9MP | **1.2 MB**（不再缩放） | **−86%** |
| 推流端跨进程拷贝 | 8.8MB DDS 读 + 8.8MB `bytes()` + 软件转色 | **0**（同进程直取） | −100% |
| 推流编码 | 软件转色 + 硬件编码 | **纯硬件** | 少一次全帧软件转换 |

> 说明：`image_raw` 仍保留发布能力，供后续需要全分辨率图的模块（录包、算法调试）使用；无人订阅时几乎不产生传输开销。

## 五、各项优化手段的验证结果

| 优化手段 | 预期收益 | 实测结果 | 结论 |
|---|---|---|---|
| **H.264 编码移入 C++ 采集进程** | −0.5~1.5 核 | **−0.79 核（−21%）** | ✅ **已采用** |
| 按需分发（全分辨率 / 640 两路） | 识别端搬运 −86% | DDS 带宽 −93%，识别 CPU 基本持平 | ✅ 已采用 |
| 限制 OpenCV 线程数为 1 | 降低多线程开销 | 相机进程 64%→50%（单路测试） | ✅ 已采用 |
| 算法图独立 QoS（best_effort） | 减少重传 | **0（无差异）** | ⚪ 保留但无收益 |
| 采集端缩放改 GPU（CUDA kernel） | −0.3 核 | **0（2.92 vs 2.93 核）** | ❌ 无效：显存流量抵消收益 |
| 降低推理输入尺寸（640→512） | 减少算力 | CPU 无变化，GPU −25% | ❌ 对 CPU 无效，且可能影响精度 |
| 重建小尺寸引擎（512） | 提升吞吐 | 识别 CPU 反升、吞吐持平 | ❌ 无效 |
| 降低推理频率（30→15fps） | 减少算力 | 每路仅 −0.08 核 | ❌ 收益过小，且牺牲更新率 |
| 多路识别合并单进程 | 省内存 | 每路吞吐 27→7.3Hz | ❌ 否决（Python GIL） |

## 六、风险与遗留事项

| 项 | 说明 | 建议 |
|---|---|---|
| 端到端延迟 | 编码参数与旧版一致（同码率、同关键帧间隔、同 RTSP 缓冲），理论持平，但未做"玻璃到玻璃"物理测量 | 用毫秒计时器拍照对比一次 |
| 资源切换参数 | 已把 GPU/CPU 取舍暴露为配置项（`algo_resize_backend`、`stream_mode` 等），默认取实测最优 | 后续做整机资源分配时按需调整 |
| 依赖变化 | 采集包新增 GStreamer 与 CUDA 依赖 | 部署镜像需确认已包含（JetPack 自带） |
| 回退能力 | `stream_mode:=python` 可一键回到旧推流路径 | 上线初期保留 |

## 附：测量方法

- **频率锁定**：`sudo nvpmodel -m 0 && sudo jetson_clocks`（GPU 931MHz / CPU 2189MHz 全程固定）
- **采样**：启动后预热 30s；连续测量 3 次各 20s，取中位数
- **进程 CPU**：读 `/proc/<pid>/stat` 的 utime+stime 增量，避免 `ps` 瞬时值噪声
- **推流校验**：每路用 `ffprobe` 确认实际分辨率与编码格式，避免"流没推上去也算省 CPU"
- **画质校验**：同一场景分别抓取新旧两版推流帧，计算 PSNR（43.8dB）

## A.3 限制 OpenCV 线程数（`algo_resize_threads=1`）

| 场景 | 默认多线程 | 单线程 | 变化 |
|---|---|---|---|
| 相机进程（有订阅者，单路） | 64.0% | **50.3%** | −13.7pp |
| 相机进程（无订阅者，单路） | 24~26% | **17.0%** | −7~9pp |
| 出帧率 | 30.0 Hz | 30.0 Hz | 持平 |

**原理**：OpenCV 的 CPU 时间 ≈ 墙钟 × 线程数。resize 1536×1920→640×640 的墙钟从 1.14ms
变为 4.92ms，但 CPU 时间从 9.1ms 降到 4.9ms（合计更省）。

## A.4 算法图独立 QoS（reliable → best_effort）

| 配置 | 采集 | 识别 | 合计 | 整机 |
|---|---|---|---|---|
| reliable（旧） | 2.32 核 | 1.05 核 | 3.37 核 | 4.01 核 / 50.1% |
| **best_effort（新）** | 2.30 核 | 1.07 核 | **3.37 核** | 3.98 核 / 49.8% |

**结论：无收益**（差异 0.02 核，在噪声内）。保留该改动仅为语义更合理（识别只取最新帧），不作为优化项。

## A.5 采集端缩放改用 GPU（CUDA 融合核）

| 后端 | 采集 ×3 | 识别 ×3 | 合计 | 整机 | GPU |
|---|---|---|---|---|---|
| `cuda`（GPU 融合转色+双线性缩放） | 1.92 核 | 1.00 核 | **2.92 核** | 3.35 核 / 41.9% | 61% |
| `cpu`（OpenCV） | 1.93 核 | 1.00 核 | **2.93 核** | 3.35 核 / 41.9% | 64% |

**结论：无收益（差 0.01 核）。** 原因：CPU resize 原本仅约 0.15 核，而 GPU 路径每帧需上传
17.7MB + 回传 1.2MB（三路 30fps ≈ 1.1GB/s 显存流量），收益被完全抵消。
**默认改为 cpu 后端**；`cuda` 保留为开关，供整机 CPU 紧张时切换。

## A.6 推理输入尺寸调整

| 采集端算法图尺寸 | 采集 ×3 | 识别 ×3 | GPU | 出帧率 | 检测频率 |
|---|---|---|---|---|---|
| 640×640（现状，5:4 被拉伸为 1:1） | 1.08 核 | 0.73 核 | 67% | 30.0 Hz | 28.4 Hz |
| 640×512（保持 5:4 比例） | 1.09 核 | 0.72 核 | 75% | 28.3 Hz | 26.9 Hz |
| 512×512 | 1.08 核 | 0.74 核 | 74% | 28.5 Hz | 28.4 Hz |

**结论：对 CPU 无影响。** 因为推理引擎输入固定为 640×640，缩小算法图后 ultralytics 仍会拉回 640，
GPU 计算量不变。

## A.12 推流链路分项成本（隔离测量）

用 `videotestsrc`（1920×1536@30fps，含信号源自身开销 0.41 核）分别测管线：

| 管线 | 进程 CPU | 扣除基线后的管线成本 |
|---|---|---|
| BGRx → fakesink（基线） | 0.41 核 | — |
| BGR → videoconvert → fakesink | 0.53 核 | **0.12 核**（软件转色成本） |
| BGRx → nvvidconv → NV12 | 0.53 核 | 0.12 核（硬件上传） |
| BGR → videoconvert → nvvidconv → NV12（旧链路） | 0.68 核 | 0.27 核 |
| 改造后（BGRx 直连硬件） | — | 0（不再需要软件转色） |

**结论**：软件转色只占 0.12 核/路；推流的主要成本其实在 **Python/DDS 侧 0.42 核/路**——
这正是本次把编码迁入 C++ 的原因。

| 频率 | `nvpmodel -m 0` + `jetson_clocks` 锁定 GPU 931MHz / CPU 2189MHz |
| 预热 | 启动后静置 30s，避开引擎冷启动（首次推理约 1.8s）与频率爬升 |
| 采样 | 连续 3 次、每次 20s，取中位数 |
| 进程 CPU | `/proc/<pid>/stat` 的 utime+stime 增量 ÷ CLK_TCK ÷ 窗口 |
| 整机 CPU | `/proc/stat` 的忙碌时间（扣除 idle/iowait）折算核数 |
| 推流校验 | 每路 `ffprobe` 确认实际分辨率/编码，避免"未推流也计入省 CPU" |
| 残留清理 | 测量前后确认视觉进程数为 0（曾因 18 个残留进程导致数据虚高，已修正） |

> **口径提醒**：未锁频时同一配置的测量结果可在 0.56~2.32 核之间波动（约 4 倍），
> 因此本报告所有结论均以锁频数据为准。
