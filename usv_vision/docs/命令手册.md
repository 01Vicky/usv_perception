按顺序抄就行。全部命令在**板子**上执行，路径以 `~/usv_ws_test` 为准。

## 0. 换一台电脑怎么开始

```bash
# ① 取代码（仓库只含两个视觉包）
git clone -b arm https://github.com/01Vicky/usv_perception.git
# 已有仓库时：git pull

# ② 本机（x86，无 Miivii SDK/无相机）只做静态自检，不编译
python3 -c "import ast;ast.parse(open('usv_vision/usv_vision/yolo_infer_node.py').read())"
python3 vision_test/vision_eval.py --selftest
python3 -c "import yaml;yaml.safe_load(open('usv_vision/config/yolo_infer.yaml'))"

# ③ 同步到板子：整包 tar，不要逐个 scp（漏附属文件会让 colcon 失败）
cd /path/to/usv_perception-arm
tar czf - usv_vision usv_vision_gmsl_cpp vision_test \
  | ssh nvidia@192.168.1.216 'tar xzf - -C ~/usv_ws_test/src/usv_perception/'

# ④ 板上编译（monorepo，只编这两个包）
ssh nvidia@192.168.1.216
cd ~/usv_ws_test && source /opt/ros/humble/setup.bash
colcon build --packages-select usv_vision usv_vision_gmsl_cpp --symlink-install
```

本机想读板子上录的包判分，需要 `source /opt/ros/humble/setup.bash`（判分依赖 `rosbag2_py`），
并把采集目录整包拷回来：`scp -r nvidia@192.168.1.216:~/usv_ws_test/vision_test/S15 .`

## 1. 启动顺序（重要）

**固定顺序：清理残留 → 起整条链路 → 确认起来 → 再录包/测数据。**

```bash
# ① 清理上一轮残留（漏了会双发布、抢设备）
pkill -f gmsl_camera_node_cpp; pkill -f yolo_infer_node; pkill -f rtsp_stream_node; sleep 3
pgrep -af "gmsl_camera_node_cpp|yolo_infer_node"      # 必须为空再往下

# ② 起链路（一条命令带起采集+识别+推流）
ros2 launch usv_vision jetson_gmsl_full.launch.py \
  cameras:="['front','left','right']" stream_mode:=internal inference:=true

# ③ 确认起来了再开始测
ros2 topic list | grep -E "image_algo|detections"
```

为什么是这个顺序：识别节点启动会订阅 `image_algo`，采集节点只在**有订阅者**时才发算法图；
先起识别再起采集没问题，但**反过来采集先起、马上测 `image_algo`** 会看到“没有数据”——
那是没人订阅，不是没出图。

## 2. 常用启动组合

| 目的 | 命令 |
|---|---|
| 只采集（不识别不推流） | `ros2 launch usv_vision jetson_gmsl_full.launch.py cameras:="['front','left','right']" inference:=false stream_mode:=off` |
| 采集 + 识别 | `... cameras:="['front','left','right']" inference:=true stream_mode:=off` |
| 全链路（含内置推流，默认） | `... cameras:="['front','left','right']" stream_mode:=internal inference:=true` |
| 推流回退到旧 Python 节点 | `... stream_mode:=python` |
| 只跑单路 | `... cameras:="['front']" ...` |
| 算法图改用压缩（暂不采用，仅验证用） | `... algo_transport:=jpeg` |
| 不发布算法图（识别改吃原图） | `... algo_stream:=false` |

板上有两个快捷脚本（等价于上表）：

```bash
~/usv_ws_test/vision_test/run_pipeline.sh off        # 只采集+识别，不推流
~/usv_ws_test/vision_test/run_pipeline.sh internal   # 全链路（推流）
~/usv_ws_test/vision_test/run_cam_only.sh            # 只采集三路
```

> 后台跑：在前面加 `setsid nohup`，输出重定向到日志，否则关掉 ssh 就没了。

## 3. launch 参数速查

| 参数 | 默认 | 说明 |
|---|---|---|
| `cameras` | `['front','rear']` | 相机列表，实际用 `['front','left','right']` |
| `inference` | true | 是否起识别节点 |
| `stream_mode` | internal | `internal`(C++内置推流) / `python`(旧节点) / `off` |
| `algo_stream` | true | 是否发布 `image_algo` |
| `algo_transport` | raw | `raw` / `jpeg`（jpeg 已实现但**暂不采用**，三路解码成本过高） |
| `streaming` | 空 | 兼容旧参数：`true`→python、`false`→off |

yaml 里的两个常用开关（不是 launch 参数）：

| 参数 | 文件 | 默认 | 说明 |
|---|---|---|---|
| `publish_only_when_subscribed` | `gmsl_camera_cpp_*.yaml` | true | 触发式发布：没人订阅就不发图（三路实测 0.66→0.44 核）；`false`=总是发，仅排障 |
| `put_timestamp` | `gmsl_camera_cpp_*.yaml` | false | 在图上叠加该帧采集时间戳（对时/延迟排查用）；**改动需重启节点**才生效 |

## 4. 起来之后怎么确认（30 秒自检）

```bash
# 话题在不在
ros2 topic list | grep -E "sensors/camera|perception/camera"

# 相机真的在出图（采集节点每秒一行，看 captured/algo）
ros2 topic echo --once /sensors/camera/front/frame_timing_json     # 加 --full-length 才不截断

# 识别有没有输出（大图不要用 hz 判准确率，只做“有没有”判断）
ros2 topic hz /perception/camera/front/detections

# 内参加载成功没（K 全零=没加载标定）
ros2 topic echo --once /sensors/camera/front/camera_info
```

采集节点日志里每秒一行：

```
pub_stats: captured=30/s raw=0/s algo=30/s algo_skip=0/s
```

- `captured` 是真正从 SDK 拿到的帧率；
- `raw` 是 `image_raw` 实际发出数（没人订阅就是 0，属正常）；
- `algo` 是算法图发出数，`algo_skip` 是“没人订阅所以没发”。

## 5. 二阶段测试流程（录包 → 判分）

```bash
cd ~/usv_ws_test/vision_test

# ① 链路已起好，开始录（600s；三路；带资源日志）
./vision_test_record.sh -s S15 -c front,left,right -d 600 -n "目标船左前方约300m"

# ② 判分（出报告）
python3 vision_eval.py S15 -o S15/report.md --tegrastats S15/tegrastats.log

# ③ 校验原始数据没被改动
cd S15 && sha256sum -c manifest.sha256

# 判定逻辑自检（不需要板子/相机）
python3 vision_eval.py --selftest
```

录多久：**正式判定至少 600s**（4.1.19 的丢帧率、4.1.21 的资源统计都按长时段更稳）；
只验证链路通不通，15~30s 就够。

判分退出码：`0`=自动项全部通过，`1`=有卡判不过（报告里看细节），`2`=包里没有可用话题。

需要录算法图（异常注入素材）：加 `--with-algo`；
需要标注图（4.1.10）：识别节点开 `publish_debug_image:=true` 后加 `--with-annotated`。

## 6. 性能测量

```bash
~/bench.sh true internal        # 识别开 + 内置推流
~/bench.sh true off             # 识别开 + 不推流
~/bench.sh false off            # 只采集
```

`bench.sh` 自带：清理 → 预热 30s → 3×20s 取中位数 → 末尾打印**一行 `RESULT|...`**（不落盘，
自己重定向存下来：`~/bench.sh true internal | tee ~/results/bench_$(date +%m%d_%H%M).txt`）。

**测之前关掉浏览器**，否则 `image_raw` 出图率会被 GUI 拉到 20Hz 上下——数字全部作废。
测完脚本会自己清理进程，但仍建议 `pgrep` 复查一次。

## 7. 推流验证

```bash
# 拉一路看有没有流、码率和关键帧
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,width,height,r_frame_rate,bit_rate \
  -of default=nw=1 rtsp://127.0.0.1:8554/cam1

# 判 GOP 必须看 key_frame（IDR），别只看 pict_type=I
ffprobe -v error -select_streams v:0 -show_entries frame=key_frame,pict_type -of csv=p=0 \
  -read_intervals "%+2" rtsp://127.0.0.1:8554/cam1 | grep -c "^1,"
```

默认地址：`rtsp://<板子IP>:8554/cam1|cam2|cam3`（按 cameras 列表顺序）。

## 8. 停止与清理

```bash
pkill -f gmsl_camera_node_cpp
pkill -f yolo_infer_node
pkill -f rtsp_stream_node
pkill -f "ros2 launch"
sleep 3
pgrep -af "gmsl_camera_node_cpp|yolo_infer_node"     # 为空才算干净
```

> `pkill -f` 会匹配到自己那条 ssh 命令行时用 `[x]xx` 写法，例如 `pkill -f "[g]msl_camera_node_cpp"`。
> **测性能前必须确认为空**，残留进程会污染所有 CPU/帧率数字。

## 9. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `image_algo` 没数据 | 没人订阅（触发式发布），起识别节点即可；或 `algo_stream:=false` |
| `camera_info` 的 K 全零 | `camera_info_url` 为空 → 没加载标定，检查 yaml 里的标定路径 |
| 识别不出目标 | 场景里没有目标；或 conf 阈值 0.40 太高、类别 allowlist 只留了 `boat` |
| `ros2 topic hz` 显示 23–27Hz | 该命令收大图会低估，**频率以包内 `capture_stamp` 为准** |
| launch 报 `malformed launch argument` | 参数要 `name:=value`，漏了冒号 |
| 录包后判分读不到 | bag 不能加 zstd 压缩；也不能预先建 `bag/` 目录 |
| 节点退出时报 `rcl_shutdown already called` | 已知小问题，运行期间无影响 |
