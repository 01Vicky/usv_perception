# 链路开销与资源占用对照账本

> **用途**：记录「原版」与「每一次修改」在**通信开销**与**资源占用**上的对比。
> **规则**：任何改动（代码、参数、QoS、分辨率、蒙板…）落地后，必须在本文件追加一行/一段，写明：
> 改了什么 → 通信开销变化 → 资源占用变化 → 吞吐变化 → 结论。
> **不许只写"优化了"而不给数**；没有测量数据就写"未测"并记录待补。

- 板卡：Jetson AGX Orin DevKit（L4T 36.4.7 / JetPack 6.2.1 / CUDA 12.6 / TensorRT 10.3.0）
- 相机：单路 `/dev/video0`，1920×1536 @ 30fps
- 模型：`yolo11n`（COCO 预训练，无 boat 类，仅用于链路性能对比）
- engine：`--fp16 --builderOptimizationLevel=0`（**不能加 `--memPoolSize`**）

## 一、测量协议（固定，保证可横向比较）

| 指标 | 采集方法 | 注意 |
|---|---|---|
| 采集出帧率 | 订阅 `frame_timing_json`（一帧一条小消息）计数 | 不能用 `ros2 topic hz image_raw`（8.8MB×30fps 下 Python 跟不上，30Hz 会误报成 16Hz） |
| 进程 CPU | `/proc/<pid>/stat` 的 `utime+stime` 增量 ÷ CLK_TCK ÷ 12s 窗口 | 不能用 `ps` 瞬时值（噪声大到能翻转结论） |
| 通信带宽 | `ros2 topic bw <topic>`，解析 `^[0-9.]+ [KMG]B/s` | 这是**订阅端收到**的速率 |
| 识别吞吐 | `ros2 topic hz /perception/camera/front/detections` | — |
| 单帧耗时 | 节点日志 `decode/infer/post` | 首帧含 engine 冷启动，必须丢弃 |

前提：测前 `pkill -f gmsl_camera_node_cpp` 清残留、确认无浏览器等 GUI 负载（否则帧率 30→18~22）。
CPU 均为**单核基准**（8 核 SoC，100% = 占满 1 核）。

## 二、主对照表

### 通信开销（订阅侧收到的图像流量）

| 版本 | `image_raw` | `image_algo` | 识别端单帧 | 推流端单帧 | 说明 |
|---|---|---|---|---|---|
| V0 原版 | 8.85 MB/帧 ×30 ≈ **265 MB/s** | 不存在 | 8.85 MB/帧 | 8.85 MB/帧 | 识别与推流都吃全分辨率 |
| V1 等价原版（新代码 `use_algo_image:=false`） | 265 MB/s | 不发（无订阅者） | 8.85 MB/帧 | 8.85 MB/帧 | A 组对照组 |
| V2 阶段A（只换驱动） | 265 MB/s | **36.5 MB/s**（1.2MB×30，实测） | 8.85 MB/帧（yolo 仍旧版） | 8.85 MB/帧 | 多一路小图，识别端不变 |
| V3 阶段B（识别吃小图） | 265 MB/s | **36.5 MB/s** | **1.2 MB/帧** | 8.85 MB/帧 | 识别端流量 −86% |
| V4 阶段C（+蒙板） | 265 MB/s | 36.5 MB/s | 1.2 MB/帧 | 8.85 MB/帧 | 流量不变，算力上升 |

### 资源占用与吞吐（实测）

| 版本 | 采集 CPU | 识别 CPU | 合计 CPU | 采集出帧率 | `detections` | 稳态 infer | 内存 |
|---|---|---|---|---|---|---|---|
| V0 原版（只采集，无消费者） | 24~26% | — | 24~26% | 30.0 Hz | — | — | 未测 |
| V1 等价原版（识别吃大图） | **29.1%** | **66.8%** | **95.9%** | 30.0 Hz | **17.6 Hz** | — | 未测 |
| V2 阶段A（驱动分发，无人订阅 algo） | **17.0%** | — | 17.0% | 30.0 Hz | — | — | 未测 |
| V2' 阶段A（+1 个 algo 消费者） | **50.3%** | — | 50.3% | 30.0 Hz | — | — | 未测 |
| V3 阶段B（识别吃小图） | **42.7~43.4%** | **33.9~48.5%** | **77.3~91.2%** | 30.0 Hz | **27.6~29.7 Hz** | 24~29 ms | **118 / 1136 MB** |
| V4 阶段C（+蒙板） | ~43% | **55.2%** | ~98% | 30.0 Hz | **22.0 Hz** | 34~40 ms | 未测 |

> V3 与 V1 对比：合计 CPU **−4.7pp**，`detections` **+57%**（17.6 → 27.6 Hz）。
> V2 → V3 的采集端上涨（17.0 → 42.7%）来自"多发一路 1.2MB"的发布路径（序列化 + 共享内存拷贝）。

### 附加验证项

| 项 | 结果 |
|---|---|
| 反压（rosbag 作可靠读者 + `SIGSTOP` 冻结） | 采集出帧率仍 **29.0 Hz**，不掉速 |
| 无订阅者时分发是否零开销 | timing JSON `published=false`，不 resize 不发布 |
| `image_algo` 理论带宽 vs 实测 | 理论 1.2MB×30 = 36 MB/s，实测 **36.5 MB/s** ✓ |
| 硬件时间戳 | 用户修复后 `driver_latency_ms ≈ 3.6 ms`（此前 SDK 返回 `timestamp=1`，延迟不可用） |

## 四、待补测量

- ~~内存占用（RSS）~~ ✅ 已支持：`scripts/record_variant.sh` 自动采 `/proc/<pid>/status` 的 VmRSS（V3 实测：采集 118 MB / 识别 1136 MB）。
- **多路相机（front/right/left 同时）**：当前只有单路数据，多路时 CPU/带宽按路数近似线性，需实测确认。
- **带 RTSP 推流**：推流端会多吃 8.85MB/帧，未纳入本轮对照。
- **长时稳定性**：连续运行 30+ 分钟的热降频影响未测。
- **真实 boat 模型**：`yolo11n` COCO 版无 boat 类，检测内容为空，仅代表链路性能。
