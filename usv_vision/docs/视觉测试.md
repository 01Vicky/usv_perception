## 1. 采集（板上）

```bash
# 先按交付方式起好采集和识别，本脚本只录不启动
./vision_test_record.sh -s S03 -c front,left,right -d 600 -n "目标船左前方约300m"
```

产出目录：

```
S03/
  bag/            消息包（不压缩，三路 10 min 约 30 MB）
  snapshot/       ros2 param dump（各节点生效参数，4.1.1 用）
  graph/          node list / topic list -t / topic info（4.1.7 用）
  scene.json      场景与版本（vision_eval 读）
  tegrastats.log  资源（4.1.21）
  bag_info.txt
```

默认只录 6 类消息（`frame_timing_json` / `camera_info` / `camera_info_algo` / `detections` / `objects` / `status`），
**不录图像**：1920×1536 单帧 8.85 MB，三路 30 Hz 约 790 MB/s，录不下也没必要——判据全在消息里。
`--with-algo` 加录 640×640 算法图，只作 4.1.24 异常注入素材；`--with-annotated` 加录标注图，供 4.1.10
（需节点侧 `publish_debug_image:=true`，开调试图时不要采 4.1.9/19/20/21 的性能数据）。

注意：**不要给录包加 zstd 压缩**。rosbag2_py 读不了 `bag_0.db3.zstd`，判分前还得先解压；
这些消息本来就小，压缩没收益。

## 4. 已知冲突（测试前先定口径）

1. **`detections` 里没有检测框**：`VisionDetection` 只有 `camera_id / class_name / class_id / azimuth / confidence / pixel_width`，
   `distance_predict / size_w / size_h` 恒为 `NaN`。框只在 `objects`（`AIVisionTargets`）里。
   F02.03 的"检测框"按 objects 核对；4.1.8 把这三个 NaN 记为"可选字段缺失"，不当失败。
2. **`objects` 没有 `output_stamp`**（只有 `header.stamp` 和 `timestamps[0].time_ms`），4.1.20 只能用 detections。
3. **分阶段耗时是节流日志**（`_timing_log_hz=0.2`，5 s 一条），10 min 约 120 条，不在报告里；需要时另解析启动日志。
4. **算法图是非等比缩放**：1920×1536 直接 `cv::resize` 到 640×640（x 缩 1/3、y 缩 0.4167），
   实测约 0.18 °/px，而正文写"640 网格约 0.14 °/px"；正文 0.06→0.14 是 ×2.33，与 1920/640=×3 不成比例。
   4.1.12 只出数并列差，不判通过/不通过（差异交负责人确认）。
5. **4.1.18 与当前阈值冲突**：fx≈955 时 2000 m 处 20 m 船长约 9.5 px，`min_box_width_px: 12` 会把它滤掉。
   要么测试前调阈值（记进 scene.json 的 params），要么该项记"当前配置不支持"。
6. **4.1.10 依赖 `publish_debug_image`**：代码默认 `False`、仓库 YAML 是 `true`、计划写实船 YAML 默认 `false`。
   上板先核对；开调试图时不得采 4.1.9/19/20/21 的性能数据。
7. **参数敏感性**：`enable_temporal_smoothing`（α=0.65）直接改善 4.1.17，`dedup_*` 直接决定 4.1.16，
   `reference_width/height: 1920/1536` 决定框坐标语义。结论只代表当前参数，改动即另建场次。

### 4.1.22 RTSP 推流（参数通过，延迟未执行）

实测：H.264 Constrained Baseline、1920×1536、30.2 fps、yuv420p；三路平均码率 3.75 / 3.75 / 3.38 Mbps（配置 4 Mbps、`control-rate=1` CBR）。

延迟 P95 ≤1.5 s 未执行：需要源端与接收端同一可见计时画面，本轮没有。

## 9. 预演确认的问题

1. **K 全零已解决**：三路 `camera_info_url` 原本为空；现已接入 MATLAB 鱼眼标定（`camera_model: scaramuzza`），4.1.4 转为通过。鱼眼模型要求等比缩放，算法图同步改为 640×512。
2. **丢帧 2.2–6.7%、最大间隔 110–220 ms**（4.1.19 不通过）：两轮差异大，怀疑是板上并发负载（rqt、ssh 统计进程）带来的，需要在静置条件下复测才能定性。
3. **GOP 口径要按 IDR 量**（4.1.22）：关键帧间隔 30 帧符合正文；若只看 `pict_type=I` 会误判成 15，因为帧间还插入非 IDR 的 I 帧。
4. **4.1.9 与 4.1.19 口径打架**：28.4 Hz 相对 20 Hz 设定达标、与图像差 1.6 Hz 也达标，但丢帧率按"输出/采集"算 5.4% 超 2%。需确认正文"丢帧率"是否按设定频率口径。
5. **4.1.18 与检测阈值冲突**：2000 m 处 20 m 船长在 fx≈955 下约 9.5 px，会被 `min_box_width_px=12` 滤掉。
6. **4.1.12 正文数值内部分歧**：0.06→0.14 是 ×2.33，与 1920/640=×3 不成比例；按 90° 视场假设实测应为 0.179，需负责人确认。

### 10.3 和计划不一致、需要人补的地方

1. **计划要求"编译"步骤留日志**（4.1.2、4.1.6）：脚本不负责编译，日志需人工 `tee`。
2. **计划要求"abnormal 时间窗"**：脚本会列出长间隔时刻，但"异常"的定性判断仍要人写。
3. **4.1.10/4.1.11 要 annotated 截图**：脚本只给帧对应与角度自洽，截图与"框是否落在目标上"必须人看。
4. **4.1.13/14/15 的数值项**：计划本轮不做标注，脚本按"未执行"输出，不做伪数值。
5. **4.1.22 的延迟**：计划要求 P95 ≤1.5 s，必须有源端可见计时源；脚本只能测参数。
6. **4.1.24**：计划要求先由视觉侧书面给出可用的软件异常入口，没有入口就停在方法确认。
