# 视觉链路性能优化报告（2026-11-11 增量）

**日期**：2026-11-11　**平台**：米文主机 NVIDIA Jetson AGX Orin 32GB（JetPack 6.2 / TensorRT 10.3）
**范围**：`usv_vision_gmsl_cpp`、`usv_vision` 两个视觉包（三路 GMSL 相机，1920×1536@30fps）
**前置版本**：`视觉链路性能优化报告261107.md`（2.90 核 / 整机 41.8%）。本文是它的增量，不重复已固化的结论。

---

## 一、结论

1. **图像话题改为"触发式发布"**：没有订阅者时，`image_raw` / `image_algo` 及对应 `camera_info` 完全不发布——
   不拷贝 8.8MB、不序列化、不写共享内存。三路相机节点合计 CPU **0.71 → 0.45 核（−37%）**。
2. **对识别与推流零影响**：一旦有订阅者（推流、录包、rviz、识别），下一轮立即恢复发布，仍为 1920×1536@30fps。
   该行为由参数 `publish_only_when_subscribed` 控制，默认开启，排障时可关掉回到旧行为。
3. 本轮同时把"为什么识别输出只有 28Hz"查清了：**瓶颈不在推理、也不在采集节点，而在大消息的 DDS 交付**（见第三节）。
   这决定了后续优化方向，不是继续压推理耗时。

---

## 二、本轮改动：触发式发布

### 2.1 机制

| 话题 | 改前 | 改后 |
|---|---|---|
| `image_raw` | 每帧都做 8.8MB 的 `toImageMsg` 拷贝并发布 | **有订阅者才发**；无订阅者零开销 |
| `image_algo` | 有订阅者才 resize，但发布路径未做订阅者判断 | 保持"无订阅者零开销"，`camera_info_algo` 同样跟随 |
| `camera_info`（raw/algo） | 每帧发布 | 跟随各自图像话题的订阅状态 |

参数：`publish_only_when_subscribed: true`（默认）/ `false`（回到旧行为，仅排障用）。

### 2.2 验证数据（三路，无人订阅场景）

| 场景 | 三路相机节点合计 CPU | `pub_stats` 表现 |
|---|---|---|
| 改前（总是发） | **0.66 核** | raw=30/s algo=0/s（algo 无人订阅本就不发） |
| 改后（触发式） | **0.44 核** | raw=0/s algo=0/s algo_skip=30/s |
| 改后 + 一个 raw 订阅者 | — | raw 立即恢复 **30/s**，帧率不变 |

> 采自同一块板、连续两次 A/B，各采样 6s 读 /proc/<pid>/stat；两次测量时板上负载均约 2.7–2.8，
> 差值为 **−0.22 核（−33%）**。此前一次同法测量为 0.71→0.45（−0.26 核），量级一致。

## 三、本轮排查发现：28Hz 的真正原因

三路全开、只跑视觉、无人为负载时，识别输出稳定在 26–29Hz，而采集端 `frame_timing` 是 30.0Hz。逐层定位：

| 环节 | 实测 | 结论 |
|---|---|---|
| 采集节点是否少发 | `pub_stats` 显示 `captured=30/s`、`algo=30/s` | **发布端确实每秒 30 条** |
| 推理是否跟不上 | C++ 原型单帧 12ms（能力 80+fps） | 不是瓶颈 |
| 交付是否丢帧 | 算法图 983KB → 订阅端 26–29Hz；**246KB → 29.9/30.0/30.2Hz**；raw 8.8MB → 约 21Hz | **丢帧随消息体积增大** |
| 队列深度 | 订阅端 1→3、发布端 1→4 | 无改善 |

**结论**：交付损失与消息体积强相关（246KB 不丢、983KB 丢 5–10%、8.8MB 丢约 30%），
要真正跑满 30Hz，方向是**减小传输的消息体积**，而不是继续优化推理。

## 四、后续方向：算法图改压缩传输（待定，未实施）

对 20 张实拍海图做了质量对照（同一 TensorRT engine，基线 640×512 bgr8 共 79 个检出）：

| 方案 | 消息体积 | 检出召回（对基线） | 备注 |
|---|---|---|---|
| 基线 640×512 bgr8 | 983KB | 100% | 当前方案，交付 26–29Hz |
| **JPEG q95** | **≈86KB** | **97.5%** | 丢失的 2 个检出 conf 仅 0.25/0.27（部署阈值 0.40 下无影响） |
| JPEG q90 | ≈60KB | 92.4% | 损失开始明显 |
| PNG 无损 | 447KB | 100% | 体积只降一半 |
| 320×256 | 246KB | 57% | 不可接受 |
| 灰度 | 320KB | 52% | 不可接受 |

成本侧：JPEG q95 编码 2.93ms/帧、解码 3.06ms/帧；三路 30Hz 折算编码约 0.26 核、解码约 0.28 核，
换来的是 DDS 写出量 **84MB/s → 7.6MB/s（−91%）** 以及发布路径开销同步下降。

**约束**：压缩只能"替换"`image_algo` 的传输格式，**不能与现有未压缩通道并行**（并行会让写出量不降反升）。

**已实现并实测（2026-11-12，结论：三路配置下不采用）**：

| 场景 | 识别输出频率 | 识别端单帧 | 三路采集节点 CPU |
|---|---|---|---|
| 单路 raw | 28.2 Hz | 9.1 ms | — |
| 单路 jpeg | **30.0 Hz** | 9.0 ms + 解码 | — |
| 三路 raw | 26.3–27.1 Hz | 24.6–26.0 ms | 0.66 核 |
| 三路 jpeg | **24.7–25.0 Hz** | 34.6–37.1 ms | **1.11 核** |

**决策（2026-11-12）**：压缩方案**暂不采用**——根因是识别端每帧多一次 JPEG 解码（实测 3.5–3.6ms/帧，
已计入日志），三路时把单帧推过 33.3ms 节拍。接口与代码保留（`algo_transport`，默认 `raw`），
重开条件是**把解码挪到硬件（nvjpeg）**，使解码成本可忽略。

单路时压缩确实能把交付拉满 30Hz；但**三路时反而更差**——JPEG 编解码把识别端单帧推到 34–37ms，
越过 33.3ms 节拍，同时采集端多耗 0.45 核。故 `algo_transport` 默认保持 `raw`，压缩通道作为可选能力保留
（小规模/单路场景、或后续换 nvjpeg 硬件编解码时再评估）。

**接口**：launch 新增 `algo_transport:=raw|jpeg`，一处下发到采集与识别两端；
采集端 `algo_transport`/`algo_jpeg_quality`、识别端 `use_compressed_algo` 均已声明。
当前 `jpeg` 只做接口占位——两端会各打一条"尚未实现，按 raw 运行"的告警并回退，**行为与现在完全一致**。
JPEG 通道本身未实现，等实测确认收益后再补。

## 五、复现方法

```bash
# 触发式发布验证（无人订阅应为 0，加订阅者立即恢复）
grep pub_stats <launch.log>                 # captured=30/s raw=0/s algo_skip=30/s
timeout 12 ros2 topic hz /sensors/camera/front/image_raw &
sleep 8; grep pub_stats <launch.log> | tail -3   # raw 恢复 30/s

# CPU 对比：改 publish_only_when_subscribed 后重启采集，读 /proc/<pid>/stat 采样 5s
```

## 六、边界与风险

1. **触发式发布只在不订阅时省钱**：推流、录包、rviz 订阅期间仍是全量发布，收益不适用。
2. **订阅者接入有一帧级延迟**（订阅生效后的下一轮开始发布），对现场使用无影响。
3. 本轮 CPU 数据受板上并发测试影响，**正式对外引用前建议在静置+锁频条件下重测一次**。
4. `image_raw` 的触发式发布**不改变**采集与推流内部链路：内置推流直接用 `cv::Mat`，不经 ROS 话题。
